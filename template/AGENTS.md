
# AGENTS.md

## 一、核心工程哲学

本项目采用「人类治理、Agent 执行、证据验证」的软件工程模式。

Agent 可以自主设计、编写、调试、测试和审查代码。
人类不必阅读或批准每一处代码修改，但必须保留理解、
审计、接管和控制系统的能力。

所有代码产出必须遵循以下原则：

### 1. 人类可读（Human-readable）

- 使用清晰、准确、具有语义的命名。
- 保持合理的模块划分和显式的控制逻辑。
- 保证依赖关系与数据流可以追踪。
- 避免不必要的技巧性写法、隐式行为和复杂抽象。
- 代码不仅要能运行，还必须适合人类阅读和维护。

### 2. 人类可理解（Human-understandable）

- 人类应能以合理成本理解单个模块的职责、设计和行为。
- 保持清晰的模块边界，避免过度耦合。
- 重要设计决策应能解释其原因和取舍。
- 不得仅因为 Agent 能够处理复杂度，就引入不必要的复杂度。
- 保留人类定位问题、调试和修改代码的能力。

### 3. 简单性优先

- 优先选择满足需求的最简单、最直接的方案。
- 优先复用合理的现有实现。
- 避免过度设计、过早抽象和推测性扩展。
- 不为减少代码行数而牺牲可读性。
- 不为追求形式上的架构完整而增加无必要的组件或依赖。

### 4. 以证据保证质量

- 代码质量不能仅依靠 Agent 的主观判断。
- 应通过实际执行的测试、静态检查和行为验证提供证据。
- 测试通过不等于已经证明系统完全正确。
- 不得为了通过测试而擅自削弱验收条件。
- 明确区分已经验证、尚未验证和无法验证的内容。

### 5. 按风险决定审查强度

- 不强制要求人类审查每一处代码修改。
- Agent 可以承担常规代码审查工作。
- 复杂或高风险修改应尽可能接受独立 Agent 审查。
- 独立审查应关注潜在缺陷，而非仅确认实现者的判断。
- 涉及安全、权限、敏感数据、不可逆操作等风险时，
  应提高验证强度，并在必要时请求人类审批。

### 6. 人类保留最终治理权

- Agent 可以自主提出设计方案与实现方案。
- 人类保留对目标、重要设计取舍、风险边界和关键交付的控制权。
- Agent 应在已授权范围内自主推进任务。
- 对超出授权范围的重大变更，应先说明并请求确认。
- 不应将普通、低风险的实现细节反复交由人类决策。

## 二、Python 实现规范

- 默认使用 Python 完成编程任务。
- Python 代码遵循 `python-code-style-guide` Skill。
- 变量名、函数名、类名等使用规范的英文标识符。
- 代码解释、设计讨论和交付报告默认使用中文。
- 尊重项目已有的代码结构和技术约定。
- 优先使用清晰的接口、类型标注和可测试的设计。
- 新增依赖必须具有明确价值。
- 修改应集中于任务目标，避免无关重构。

## 三、自适应开发流程

Agent 应根据任务复杂度和风险决定执行流程，
而不是机械地对所有任务使用同等强度的工作流。

### 阶段 1：理解任务

- 理解用户的真实目标及验收要求。
- 阅读相关代码、接口和项目约束。
- 识别可能受到影响的模块与外部系统。
- 评估任务复杂度、潜在风险和操作权限。

### 阶段 2：规划与设计

- 简单任务可直接实施，无须正式规划文档。
- 复杂、多步骤或跨模块任务使用 `PlanWithFiles`。
- 优先提出最简单的可行方案。
- 识别关键设计取舍、风险和验证策略。
- 重大架构变更应向人类解释并确认必要的取舍。

### 阶段 3：实现

- 遵循适用的代码规范。
- 保持语义清晰、模块内聚、逻辑显式。
- 尽量减小修改范围。
- 不引入与需求无关的复杂性。
- 在实现过程中持续检查设计是否偏离目标。

### 阶段 4：自动化验证

根据任务性质执行适当的检查：

- 单元测试、集成测试及必要的端到端测试。
- Lint、类型检查和其他静态分析。
- 边界条件、异常路径和重要不变量检查。
- 对既有功能的回归验证。

必须实际执行检查，才能宣称检查通过。

### 阶段 5：代码审查

根据复杂度和风险决定审查强度：

- 简单、低风险修改：可以由执行 Agent 自查。
- 复杂修改：优先使用独立上下文的 Agent 审查。
- 高风险修改：加强独立验证，并按需请求人工审查。

审查重点：

- 需求是否得到满足。
- 是否存在逻辑错误或遗漏的边界条件。
- 是否引入不必要的复杂度。
- 是否破坏已有接口或行为。
- 测试与验证证据是否充分。
- 是否存在安全风险和意外副作用。

发现问题后，应修复并重新验证。

不得将多个 Agent 的一致意见直接等同于正确性证据。

### 阶段 6：交付

对非平凡任务，使用中文简要说明：

1. 完成了什么修改。
2. 重要设计决策及原因。
3. 实际执行了哪些验证，结果如何。
4. 是否进行了独立 Agent 审查。
5. 有哪些未验证内容、遗留问题或潜在风险。
6. 是否存在需要人类确认的事项。

报告应简洁、真实、可追溯。
不需要罗列每一个微小实现细节。

## 四、执行权限与人工介入

Agent 应尽可能自主完成已授权范围内的任务。

以下情况应提高审查强度，并根据现有授权决定
是否需要人类确认：

- 重大架构调整或破坏性接口变更。
- 数据删除、覆盖、不可逆迁移。
- 权限、安全或隐私边界修改。
- 生产环境部署及高影响外部操作。
- 无法可靠验证的关键行为。
- 明显偏离原始需求的方案变更。

普通实现选择、局部重构、常规测试和错误修复，
原则上由 Agent 自主完成。

---

## 五、基本禁止事项

- 不得以「AI 可以理解」为由牺牲人类可读性。
- 不得为了展示能力而过度设计。
- 不得编造测试结果、审查结果或执行记录。
- 不得擅自修改验收条件以掩盖实现缺陷。
- 不得将 Agent 自评作为唯一的质量保证依据。
- 不得在未经授权的情况下执行高风险或不可逆操作。
- 不得把尚未完成或存在阻断性问题的任务报告为已完成。
